# 余烬首次安装引导

## Contract

输入是用户已确认的首次安装范围、程序目录、数据目录、名称及模式。安装阶段输出独立应用环境、新文档库、余烬系统项目、三项基础 Skill 和程序目录内的真实安装记录，**此时不创建任务卡**。配置执行器后，由日常 `ember` Skill 使用普通建任务接口，把当前对话创建为第一张真实任务卡；它属于本机的余烬系统项目。最后用户确认完成后，完成这张卡并受控移除本库 `ember-init`，保留日常与建项目 Skill、全部项目、任务和资料。

每一阶段简短说明“正在做什么、验证了什么、下一步是什么”，不要只扔出一串命令。沿用当前对话已确认的信息，只补问影响结果的关键缺项，一次一项；已经授权的新目录安装不重复索取许可。默认名称余烬、端口 8783、空白业务模式。先讲用户将看到什么、需要回答什么；技术命令由 AI 执行。安装记录、第一次建卡、练习建项按顺序发生，不能提前替用户完成教学步骤。

**调用即开始引导。** 网站安装提示就是本 Skill 的入口。先从官方发行初始包读取本文件和安装脚本，在当前对话中直接开始，不要求用户再发送“激活 Skill”。“激活”指当前 AI 读取并执行本流程；程序与 Skill 文件不会自行发起 AI 对话。三项 Skill 随初始包和程序 wheel 提供，建立文档库时再复制到其中；不要求新用户另找一个初始化 Skill。若工具不能读取文件或执行本机命令，明确说明缺少的能力，不声称已安装或已激活。

首次面向用户统一称“文档库”，首次解释它就是命令中的“工作区 / workspace”。不要让新用户先理解虚拟环境、端口、执行器或模型；这些由 AI 检查。收到安装请求先问文档库位置，确认后才创建。安装完成必须继续展示真实目录并等待反馈，不能以“安装成功，请自己调用初始化 Skill”结束。

bootstrap 完成后的空白业务模式是一个系统项目、零任务；示例模式是三个项目、八项原有示例任务。日常 Skill 执行建卡后分别为一项真实任务或九项任务。用户在后续教学中确认建立练习项目时，再增加一个真实登记、明确标注练习用途的项目，它不是自动生成的业务数据。技术测试一律放在隔离工作区，成功后仅清理脚本自己创建的测试目录，失败现场保留。通过测试不等于用户接受，不自动正式交付或完成任务。

## When to Use

- 新电脑首次安装本机余烬，并带领用户走完首次使用。
- 使用本版已安装的余烬在全新目录建立独立工作区；不改写旧工作区。
- 验证新安装的规则、项目、首任务、资料、交付和本机工作台。

## References

- 先读同目录 `scripts/bootstrap.py`，使用标准库编排安装和隔离验证。
- 安装后读工作区 `AGENTS.md`、`SOUL.md`、`MEMORY.md`、`RESOLVER.md`、`skills/RESOLVER.md` 与 `templates/task-card.md`；系统级 AGENTS.md 是规则正本。
- 三项 Skill 的唯一正文在 `.agents/skills/ember-init`、`ember`、`ember-project`，`skills/manifest.json` 及 Resolver 登记它们。
- 首个业务项目使用 `ember-project`，日常任务交给 `ember`；不要复制私有系统建项规范。
- 执行器登记使用程序 `ember.executors.ExecutorRegistry` 或工作台同名 HTTP 接口，字段与行为见仓库 `docs/api.md`；不直接改写本机软件 JSON。

## Phases

### 1. 欢迎，先确认文档库位置

如果用户尚未给出文档库路径，第一条用户可见回复采用下面的结构；替换为当前机器实际的建议路径，只问这一个问题：

> 欢迎你安装余烬！我会带你一步一步完成系统指引。
>
> 首先确定你的文档库放在哪里。它会保存项目说明、任务记录、输入资料和成果，关掉软件后这些文件仍然在。
>
> 我建议新建在 `<当前用户主目录>/Ember-Workspace`。你想用这个位置，还是指定另一个文件夹？

等待用户回答，不同时追问业务项目、分类或软件配置。如果路径已在当前对话确认，欢迎后直接复述并沿用，不重复问。用户不懂路径时，解释这是电脑上的一个普通文件夹，提供一个基于本机用户目录的具体建议。只有用户自己提到 VS Code 时说明：VS Code 的“打开文件夹”只是编辑器当前打开的位置；它既不是余烬程序目录，也不会替余烬创建或登记文档库。安装不依赖 VS Code。

在准备安装期间自行检查 macOS / Linux 与真实 Python 3.10+ 解释器，不能假定系统 `python3` 合格；检查本机是否已有安装或默认文档库，不读取其中业务内容。发现已有工作区先说明现状，本 Skill 不覆盖旧库。沿用名称和模式，未指定时使用余烬 / 空白业务模式 / 8783，不为这些默认项再发一轮问卷。非空、符号链接、包含关系或端口冲突时停止，不删除现场。

### 2. 说明程序位置，确认本次创建范围

确认文档库位置后，说明程序目录保存运行程序、`.venv` 与安装收据，文档库保存规则、项目、任务、输入、草稿和正式成果。未给程序目录时建议当前用户主目录下的 `Ember-App`，核对两个目录独立、互不包含。用已确认路径展示简短安装计划，只补问缺少的确认：

> 你的文档库是 `<已确认路径>`。程序放在 `<程序路径>`，与文档库分开保存。我会装上自带的三个 Skill，建立基础文件夹，先保存安装记录；等软件配置好后，再带你把这次对话做成第一张任务卡。默认不加入虚构业务。按这个计划开始可以吗？

已有相同范围的明确授权就直接执行。空业务模式不创建示例客户；安装过程会登记 `ember` / 余烬 / `kind:system` ，不创建“余烬初始化验收”任务。本次安装不包含任意业务项目、软件登录或旧资料迁移。不要在 bootstrap 之前手工填充文档库，否则其拒绝非空目录的检查会阻止安装。

### 3. 安装独立环境

使用实际解释器和路径，不猜执行器或模型：

```text
<真实Python> <Skill目录>/scripts/bootstrap.py --app-dir <程序目录> --workspace <数据目录> --mode empty|example --name <名称> --port 8783 --executor <实际调用工具>
```

实际调用工具可为 opencode、codex、workbuddy、claude-code 等；未知则 manual，不能填模型名。独立初始包含 `ember-init`、`ember`、`ember-project` 三个 Skill 文件夹，init 内含 `assets/ember-0.10.0-py3-none-any.whl`；没有 wheel 时用固定 v0.10.0 地址。开发可传 `--source`。PyYAML 依赖仍须网络或缓存，不声称完全离线。

### 4. 保存安装记录，保留空任务列表

脚本登记 `projects/ember.md` 和系统注册，说明它负责本机余烬的安装与维护。安装阶段、已确认目录和技术检查保存在程序目录的 `installation.json` 与成功时的 `installation-report.md`（失败为 `installation-failure.md`），不是任务输入或交付。此时空白文档库的任务列表应为零；不调用 `create_task`，也不为说明文件制造任务或交付文件夹。失败保留程序目录的收据、报告和检查现场，不重复初始化或编造首任务。

### 5. 回读三项基础 Skill

检查工作区规则、任务模板、三项 Skill 正文、版本、脚本、manifest 和 Resolver。安装到工作区的 Skill 不等于自动加入所有客户端：若当前工具不发现 `.agents/skills`，让用户按该客户端规则导入或显式读取，不改其账号、权限或模型配置。

**先展示文档库，再继续指引。** bootstrap 返回后先回读实际收据和文件目录，把本轮已经建立的结构展示给用户。下面是阅读顺序与中文说明，不能把示意树当作执行证据；必须只显示实际存在的目录，并将根替换成已确认的绝对路径：

```text
<文档库绝对路径>/
  projects/           项目与系统说明
  tasks/active/       正在做的任务
  tasks/completed/    已完成的任务
  inputs/             任务输入资料
  delivery/draft/     待确认的草稿
  delivery/formal/    已确认的正式成果
  inbox/              临时收集的资料
  reports/            任务检视报告
```

补充说明系统规则文件已经放在文档库根目录，三个 Skill 已在 `.agents/skills/`，版本和路由登记在 `skills/`。给出可点击的文档库路径；当前工具支持文件浏览时展示该目录，不自动启动 VS Code 或其他软件。说明空的基础目录正常，任务子目录只在实际资料或成果出现后创建。

结束这一轮只问：

> 文档库和基础文件夹已经建立在 `<实际路径>`。以后项目、任务、资料和成果会按这些位置保存。这个位置和安排可以吗？

等待用户反馈后，再依次进行“当前 AI 工具与日常 Skill → 对话任务卡 → 用户在工作台确认 → 简单练习项目”；不要一次列出所有后续问题。若希望换位置，不重新初始化或直接搬动已有库，先说明已产生安装记录，再确认单独调整范围。这句确认只接受目录阶段，不等于整项安装验收、正式交付或任务完成。bootstrap 内部已自动完成的隔离验证照实报告，不能声称还没运行。

### 6. 回读安装记录与技术检查

bootstrap 已先检查真实文档库，再在自己的临时文档库中测试项目、任务、输入、交付、引用和本机 HTTP。模拟数据不留在用户文档库。回读程序目录内 `installation.json` 的状态、阶段、检查和报告路径，再读取收据 `report_path` 指向的实际成功 / 失败报告，运行 check。成功说明“系统已经装好，接下来配置你正在使用的 AI 工具”；失败说明卡在哪一步，先修复，不进入实操引导。技术通过不代表用户验收，脚本没有替日常 Skill 创建任务。

### 7. 配置当前 AI 工具，装好日常 Skill

优先使用当前会话已经在用的 AI 工具。执行器就是用户选择的 AI 软件；它已经能进行这次对话，通常不需要重复安装。区分三件事：bootstrap 的 `--executor` 只记录工具名；默认执行器登记决定工作台以后打开哪个软件；全局日常 Skill 让该工具能找到文档库并操作任务。三者不能互相代替。

从宿主上下文或用户已确认的选择识别当前工具，用只读发现检查它真实的应用 / 命令路径。不能按模型名、PATH 首项或“发现了某软件”猜当前工具；桌面应用、CLI 与编辑器扩展也不能混为一谈。身份或路径不明确时一次只补问一个缺项。当前工具不可用或不支持全局 Skill 时如实说明，提供显式读取文档库内 Skill 的继续方法，不静默安装另一款软件。

向用户展示已查明的工具名称和软件路径，以及日常 Skill 的实际安装位置，说明：

> 接下来，我建议把你现在用的 `<AI 工具>` 设为余烬的默认执行器，并装好它使用的日常任务 Skill。以后想换工具，可以到工作台的“设置 → 执行环境 → 修改配置”。按这个安排配置可以吗？

这次确认覆盖已展示的软件登记和 Skill 安装；已有相同范围授权就直接执行。不要求用户再手动跑命令。保留现有软件清单；如已有不同默认项，先说明原项与新项的差异，再按用户选择保存。

执行顺序：

1. **登记默认软件。** 用程序 Python 调用 `ExecutorRegistry.snapshot()`，配置可读才继续；只读 `discover()` 返回候选。保留 `executors` 原有条目，按解析后的真实路径复用或加入当前工具，每项仅含 `id`、`label`、`kind`、`path`，`kind` 为 `app` 或 `command`。payload 使用 `executors`、选中的 `default_executor` 和当前 `expected_revision`；先 `validate()` 再 `save()`。也可使用工作台 `/api/executors/discover`、`check`、`save`，POST 带 `/api/state` 返回的 CSRF token。保存后回读默认项、`registry_readable` 与 `ready`；不得直接写 JSON、丢弃其他软件或绕过版本冲突。配置保存在本机 `~/.config/ember/executors.json`，不写入文档库。只检查路径，不启动软件，不把 `ready` 当作模型 / 登录验证。
2. **登记默认文档库。** 回读安装收据 `default_workspace` 和 `~/.config/ember/workspace.json`。bootstrap 已执行 `ember use`，不要重复覆盖；若为 `kept-existing`，展示旧库与新库，用户明确选择后才用 `<程序Python> -m ember use <新文档库> --replace`。
3. **安装全局日常 Skill。** 按当前工具的真实发现规则确认用户级 Skills 目录（例如 Claude Code `~/.claude/skills`、Codex `~/.agents/skills`、OpenCode `~/.config/opencode/skills`），运行 `<程序Python> -m ember install-skill --target <目录>`。回读返回 `path` 下的 `SKILL.md`（即 `<目录>/ember/SKILL.md`）及版本。`unchanged` 为同版，`upgraded` 为官方旧版升级；本地改过的副本停止、不覆盖。安装目录会被记住，以后升级程序后运行不带参数的 `install-skill` 可更新这些目标。初始化和建项目 Skill 已在文档库内，日常 Skill 会路由读取它们，不需要重复全局安装。当前 AI 显式读取新日常 Skill 后继续，不能仅凭复制成功声称客户端已热加载。
4. **验证定位。** 在文档库外用程序 Python 执行 `-m ember where` 和 `-m ember check`，确认默认库就是本次库。若用户选择保留其他默认库，后续显式指定本次库，并如实说明自动定位仍指向旧库。

向用户提示的设置入口只负责更换默认执行器；设置中的 Skills 区目前显示登记与版本，不能声称有客户端全局 Skill 安装按钮。安装不需要 MCP，也不改软件账号、权限或模型配置。

### 8. 用日常 Skill 创建第一张任务卡，请用户检查

对用户说：

> 软件配置好了。现在我们实际试一次：我会把刚才这段安装和配置的对话，做成你的第一张任务卡。以后换一个对话，也可以从这张卡继续。

实际读取刚安装的 `ember/SKILL.md`，按它的定位、检查和普通建任务流程操作。先核对本次库和系统项目、安装收据；正常首次安装此时没有真实安装任务。若对话中断后恢复，先按已知 ID 或登记了 `ember-init:installation-receipt` 输入的系统任务查找；匹配同一次安装才续接，有歧义先核对，不只按标题猜、不重复建卡。不要把示例任务当作用户首卡。

先核对本次文档库服务是否已运行；未运行才按收据 `startup_argv` 启动，已运行则复用并核对工作区，不重复启动。运行服务时通过带 CSRF token 的 HTTP 接口写入；未运行时用 `workspace_lock(workspace)` 包住 `Workspace` 写入。日常 Skill 执行以下普通操作，不调用安装脚本代建卡：

1. `create_task` / POST `/api/tasks`：标题“余烬首次使用”，`project:ember`、`work_type:system`、`task_kind:task`、`artifact_mode:none`、真实 `executor`、实际 `skills_used:[ember-init,ember]`。目标是完成本次安装和首次使用，描述写用户确认的选择及要求，不假造聊天或业务。这里没有待交付文件，安装报告是安装证据，不为了完成任务制造草稿。
2. 用 `update_task` / POST `/api/tasks/<id>` 记录实际安装结果、软件登记、日常 Skill 使用结果和下一步。将程序目录当前 `installation.json` 完整文本用 `add_material(kind=input,name=安装记录.json,source_locator=ember-init:installation-receipt,purpose=本次安装及技术检查的只读记录)` 保存为输入快照；同名只读回查并比对，不覆盖。报告可保存为另一份文字输入，来源注明实际报告路径；不复制账号、密钥或无关对话。
3. 建卡成功而输入登记失败时，保留并续接刚返回的 ID，补输入，不重新建卡。记录 ID 是本轮后续流程的唯一跟踪卡。
4. GET `/api/state` 的 `data.tasks` 按 ID 回读正文、工具、Skill 与输入；没有 GET `/api/tasks/<id>`。检查健康与任务台、项目、检视、资料、设置入口。刷新或重新加载工作台后打开实际 URL 的 `#task/<id>`，只切换 hash 不会重取数据。确认 `ember` 系统项目里确实出现这张卡。无法保持服务运行时如实说明，不给“已经能打开”的假保证。

这一轮只问：

> 第一张任务卡建好了。请打开工作台里的“余烬首次使用”，看看里面的目标和安装结果是否准确。有没有需要补充的地方？没有的话，告诉我“OK”，我们再练习建一个项目。

等待用户反馈。有遗漏就用日常 Skill 更新同一卡，再请检查；明确 OK 后才能进入练习项目，并将实际反馈追加到任务日志。这个 OK 只确认任务内容，不等于整个引导完成或授权删除初始化 Skill。

### 9. 最后一项练习：用建项目 Skill 建一个简单项目

任务卡检查得到用户 OK 后，读取文档库内的 `ember-project/SKILL.md`，通过其查重、完整方案确认和受控登记流程建立一个明确的练习项目。给用户一个简单建议，一次只问这一项：

> 最后，我们练习建一个项目。建议叫“余烬练习项目”，只用来熟悉项目说明和任务管理，暂不关联外部资料文件夹。用这个名字和用途可以吗？

技术方案由 AI 准备并以易懂的摘要展示：建议 ID `ember-practice`、`kind:project`、练习用途和范围、空 `locations` 与未分类的 `category`，以及独立项目说明和实际写入位置。说明必须明确它是用户自己的首次使用练习，不代表真实客户或业务；它会保留在文档库中，不在检查结束后自动删除。用户有真实简单项目时可改用其确认名称与用途，不编造业务事实。用户选择跳过时记录跳过，不替他建项。

先只读查重并展示该方案，再取得用户对相同方案的确认；已确认全部字段就不重复询问。用户改名或改用途时相应修订方案；同名 / 同 ID 先请其选择复用或修改，不能重复创建。按 `ember-project` 使用既有 `project.py` 的方案哈希确认路径，或服务运行时按该 Skill 的 HTTP 分支重新查重、提交确认的项目字段，再单独在原安装任务登记实际 Skill 和建项日志；接口不会自动完成任务审计。建项后从 `/api/state` 的 `data.projects` 按 ID 回读项目与 `overview`，并只读核对 `projects/<id>.md`，运行 check，刷新或重新加载工作台后，再给出 `#project/<id>` 链接并展示项目名称、用途和说明；不能只在已打开的旧页面切换 hash。安装任务仍属于 `ember` 系统项目，不移到练习项目，不为了演示再造任务或交付文件。

### 10. 用户确认完成，移除一次性向导

先回读任务卡、练习项目和实际软件配置，确认没有未解决问题。展示这次真实完成的三件事：当前 AI 工具已配置、第一张任务卡已保存、练习项目已建立；若用户明确跳过项目或有失败，照实写明，不能说全都完成。告诉用户以后在“设置 → 执行环境 → 修改配置”更换工具，日常工作使用 `ember`，建项目使用 `ember-project`。

最后只问一个明确的问题：

> 新手引导走完了。你的任务卡和练习项目都会保留，日常任务和建项目功能也会继续使用。确认完成后，我会把文档库里这份一次性安装向导移除，以后就不会再出现在这里的 Skill 列表中。现在确认完成并移除安装向导吗？

必须等待这次最终确认。之前的目录确认、任务卡 OK 或建项确认不能代替它。用户要求保留向导就保留；中途暂停、未明确回答或有未解决问题时不清理。如果用户明确跳过项目，记录跳过并保留向导，本轮不得声称完整实操和自动移除已经完成。

收到“完成并移除”的确认后：

1. 在仍活跃的原任务追加最终真实结果、练习项目 ID / 用途、用户最终确认和拟移除范围；没有真实后续事项就不虚构。通过既有 `complete_task(id,{confirmation:true})` 或 POST `/api/tasks/<id>/complete` 完成本次 `artifact_mode:none` 的任务。不能用普通状态更新绕过完成门禁；不得制造正式交付文件。
2. 运行服务时 POST `/api/onboarding/remove-init-skill`，payload 仅为 `{task_id:<已完成的首任务ID>,confirmation:true}`，使用当前服务的 CSRF token。服务未运行时用程序 Python 执行 `-m ember.onboarding_completion --workspace <文档库> --task-id <ID> --confirm`。清理接口核对本次安装记录、已完成任务及实际 Skill 历史，只处理固定的 `.agents/skills/ember-init`，并同步 manifest / Resolver 与完成记录。不能自行使用 `rm -rf`，不能传任意路径；检测到用户改过的向导就保留并说明。
3. 清理失败时，原任务已完成的事实保留；只重试同一清理动作，不再建卡、不再次完成任务、不声称已删。成功后 check，并回读 `/api/health`、`/api/settings` 和已完成任务 / 项目。刷新工作台，确认仍正常、当前 Skills 仅保留 `ember` 与 `ember-project`，再给用户结果。

移除仅指当前文档库内的初始化 Skill；程序包中的原版、原始下载包和用户自行安装的其他全局副本不在这个动作范围。它们不影响本库的两项日常 Skill；将来新建文档库仍可通过 `ember skill-path` 读取程序自带初始化指引。升级程序或更新全局日常 Skill 不会重装已经移除的文档库向导。

已有同版程序只建新库时，也必须保留独立的本次安装记录，不能覆盖原应用目录的另一库收据；先确认独立记录位置和现有安装支持的流程，不用旧收据伪造本次 ready。已有工作区不在本 Skill 升级或清理范围。

## Output Format

简短中文阶段总结：实际程序 / 文档库目录、默认执行器与以后修改入口、全局日常 Skill 的安装和实际调用结果、第一张真实任务卡的链接及用户反馈、练习项目链接或跳过事实、安装记录、技术检查与服务运行、最终确认及向导是否实际移除。任务尚未验收就写明，不把程序安装成功等同于完成整个首次使用。

## Anti-Patterns

- 不覆盖、重置或迁移已有工作区，不删除失败现场或用户文件。
- 不把模拟测试任务留在真实空业务工作区，不自动创建虚构业务项目。
- 不读取私有余烬、NAS、真实历史任务或认证配置作为模板。
- 不重复安装已在使用的 AI 软件，不猜默认执行器、不静默改用另一软件；仅按本次明确选择登记并安装日常 Skill。不配置插件、MCP、凭据、邮件、守护程序或公网监听，不自动运行 AI，不覆盖改过的 Skill。
- 不用测试通过代替人工验收，不制造占位交付或替用户正式交付、完成任务。
- 不恢复已撤下的归档模块，不把安装授权当作任意建项或资料迁移授权。
- 不把复制 Skill 文件称为自动开启 AI 对话；不让新用户再发一次激活命令，不连续抛出一串问题，也不跳过文档库展示就开始业务建项。
- 不在配置执行器前预建首卡，不把续写脚本预建卡称为日常 Skill 首次建卡测试。
- 不在最终明确确认前移除向导，不删程序源、全局 Skill、练习项目、任务、输入或安装记录；不把清理失败说成成功。
- 不把文件存在、路径可用或程序测试通过当作日常 Skill 已实际执行；不跳过任务卡的用户检查，不把练习项目当作默认虚构业务或在验证后自动删除。

## Tools Used

文件读取、终端与浏览器。安装使用参数数组启动子进程；安装记录使用 `onboarding`，首任务由日常 Skill 使用既有 `Workspace` / HTTP 创建，建项使用 `ember-project` 的既有受控接口，不拼接任意 shell 命令。
