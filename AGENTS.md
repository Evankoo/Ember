# Ember contributors

This repository is generated: the maintainer edits these files in the private repository's `public/` folder and exports them with its export tool. A change committed here directly is reported as drift by the next export and blocks it.

Keep this package local, small and readable. Workspaces contain user data; never add a real workspace, secret, account configuration or production system history to this repository.

- Markdown task cards and actual files are canonical. Preserve source evidence and refuse silent overwrite.
- Project ownership, task-line references, presentation importance and task lifecycle are separate.
- Review reports do not authorize merge, split, completion or deletion.
- Keep the server on loopback. Software launch is limited to the explicitly confirmed saved default: open a local app or a new terminal with a quoted executable path. Never accept request-provided commands, prompt arguments, model credentials or remote bridges.
- Machine software preferences belong only in the user's private Core configuration, never in a workspace or this repository. Discovery and checks are read-only; launches must not submit prompts or mark tasks executed.
- `src/ember/ember_ui/` (the shared page templates, Markdown rendering, stylesheets and scripts) is copied verbatim from the full workbench's `ui/ember_ui/` by `tools/sync_workbench_styles.py`, and `web/assets/workbench-pages.css` is generated by it; never hand-edit either. Server-rendered pages build their data in `src/ember/pages.py` and render it with the shared template. Put Core-only styles in `web/app.css`, reuse the workbench's markup and class names, and pass local data and actions to the shared scripts instead of rewriting them in `app.js`.
- Pages must render the full workbench's markup and class names. `tools/check_workbench_parity.py --source <workbench>` compares every page with the running full workbench; each remaining difference needs an entry with a reason in `docs/workbench-parity.json` (`intentional` or `pending`). After changing `web/` run it with `--write-record`; the tests fail while `docs/workbench-parity-record.json` does not match the shipped UI files.
- Release only after `tools/release_check.py --source <workbench>` passes: tests, stylesheet sync, page parity and a changelog section for the version.
- A GitHub release is titled `vX.Y.Z · <one-line summary>`. Its notes are two to four short change bullets, then an `**安装**：` line naming `ember-init-X.Y.Z.zip`, an `**升级**：` line, and one line linking that tag's `CHANGELOG.md`. Attach only `ember-init-X.Y.Z.zip`, which carries the wheel; the updater verifies it by GitHub's asset digest or the mirror's `SHA256SUMS`, and GitHub supplies the source archives.
- Reuse the shared visual tokens and reading hierarchy. Verify populated, empty and error states and narrow layouts.
- Run `python -m unittest discover -s tests -v` after changing storage or HTTP behavior. Verify a built wheel includes the UI, fictional examples and font license before release.
- Workspaces are Chinese or English, fixed when created (`src/ember/language.py`). The program keeps Chinese names as internal identifiers and `Vocabulary` maps them to the names written on disk; a Chinese workspace must stay byte-for-byte unchanged. Interface and generated text is written in Chinese and translated through `src/ember/locales/en.py`: server code uses `ember.i18n.t`, and pages from the shared templates are translated in the browser by `web/i18n.js`. Every new user-visible string needs an English entry; `tests/test_language.py` checks every English page for leftover Chinese. English rule templates and Skills live under `locale/en/` beside the Chinese originals and replace them when an English workspace is installed.
- Keep changes within the requested scope. Do not rewrite unrelated code or data.
