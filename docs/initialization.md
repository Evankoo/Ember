# 一问一答完成首次使用

首次引导的顺序是：**确认文档库 → 安装并保存记录 → 配置当前 AI 工具 → 用日常 Skill 创建第一张任务卡 → 用户检查 OK → 建练习项目 → 最终确认完成并移除一次性向导**。安装脚本不抢先建任务；每个问题都让用户看到具体结果再回答。

## 用户会经历的对话

**第一轮：文档库放在哪里。**

> 欢迎你安装余烬！我会带你一步一步完成系统指引。先确定文档库放在哪里：它会保存项目说明、任务记录、资料和成果。我建议放在 `<本机实际建议路径>`。你想用这个位置，还是另一个文件夹？

用户回答后，AI 检查路径，说明独立的程序安装位置，只补问尚未确认的安装计划。文档库就是命令里的 workspace，安装不依赖 VS Code；编辑器“打开文件夹”也不会替用户创建文档库。默认空白模式、名称余烬、端口 8783，技术参数由 AI 核对，不向新手抛出一整页问卷。

**第二轮：装好后看一眼目录。**

AI 安装程序、规则和三个自带 Skill，创建负责安装维护的余烬系统项目。安装记录保存在程序目录，此时任务列表为空。回读实际目录，用中文解释项目、任务、输入、草稿和正式成果的位置，再问：

> 文档库和基础文件夹已经建好了，位置是 `<实际路径>`。这个位置和安排可以吗？

确认后再往下走；如果有错误，先修复，不用后面的练习掩盖安装问题。

**第三轮：配置正在使用的 AI 工具。**

> 接下来，把你现在用的 `<工具名称>` 设为余烬的默认 AI 工具，并装好它使用的日常任务 Skill。以后想换工具，可以到工作台“设置 → 执行环境 → 修改配置”。按这个安排配置可以吗？

AI 先核实实际宿主工具、软件路径和用户级 Skill 目录。用户确认后由 AI 登记和安装；已使用的软件不重复安装。默认软件登记和日常 Skill 安装是两个真实动作，不能仅写任务的 executor 字段就称为配置完成，也不能把路径可用说成登录或模型可用。

**第四轮：亲眼看到第一张任务卡。**

> 软件配置好了。现在我们实际试一次：我会把刚才这段安装和配置的对话，做成你的第一张任务卡。以后换一个对话，也能从这里继续。

AI 实际读取并执行 `ember`，用普通创建接口建立“余烬首次使用”，记录目标、已确认选择、安装结果、实际工具和下一步，将安装收据保存为输入快照。它是第一次真实建卡，不是更新安装脚本预先生成的卡。中断恢复时续接已建立的同一卡。

刷新工作台，打开该卡，再问：

> 请看看这张任务卡的目标和安装结果是否准确。有没有需要补充的地方？没有的话，告诉我“OK”，我们再练习建一个项目。

有遗漏就修改原卡；必须等用户明确 OK，才进入下一轮。

**第五轮：建立简单练习项目。**

> 最后，我们练习建一个项目。建议叫“余烬练习项目”，用来熟悉项目说明和任务管理，暂不关联外部资料文件夹。用这个名字和用途可以吗？

AI 读取 `ember-project`，先查重并展示名称、用途、范围和独立说明，用户确认后才创建。用户可以改用自己的真实简单项目，不编造客户或业务。写入后刷新工作台、打开项目说明，项目会保留。首任务仍属于余烬系统项目，建项过程记录在原卡，不为演示再建一张假任务。

**第六轮：完成，并移除一次性向导。**

> 新手引导走完了。你的任务卡和练习项目都会保留，日常任务和建项目功能也会继续使用。确认完成后，我会把文档库里这份一次性安装向导移除，以后就不会再出现在这里的 Skill 列表中。现在确认完成并移除安装向导吗？

等待用户最终确认；前面的目录确认、任务卡 OK、建项确认都不能代替这一句。用户要求保留就保留；明确跳过项目时照实登记，保留向导，不声称已经完成整套实操与清理。

确认后先通过普通完成接口完成首任务，再由固定范围的移除接口删除本库初始化 Skill 并同步登记。用户修改过的向导会保留并报出原因；错误只重试清理，不重复建卡或完成任务。最后重新检查工作台、任务和项目，确认日常 / 建项目两个 Skill 正常。

## 安装包、记录和任务分别在哪里

网站提示要求 AI 直接读取并执行发行包内的 `ember-init`。用户不用安装完再输入“激活”；Skill 文件本身不会发起聊天，提问由当前 AI 执行。

初始 ZIP 有 `ember-init/`、`ember/`、`ember-project/` 三个同级目录，init 内附同版本 wheel。wheel 包含程序、三个 Skill、系统规则、页面、虚构示例及字体许可证。程序依赖 Python ≥3.10、macOS / Linux；PyYAML 仍需网络或缓存，不声称完全离线。

```text
程序目录/
  .venv/                         独立程序环境
  installation.json              安装选择、阶段、检查和启动参数
  installation-report.md         成功时的技术安装记录
  installation-failure.md         失败时的说明（仅失败时生成）
文档库/
  projects/ember.md             自动建立的系统项目
  tasks/active/                   安装刚结束时为空
  tasks/completed/                最终确认完成的任务
  inputs/                         首卡建立后保存安装记录快照
  delivery/draft/                 有真实成果才创建任务子目录
  delivery/formal/
  inbox/ reports/
  .agents/skills/                 初始三项，确认移除后两项
  skills/manifest.json            当前 Skill 登记与引导完成记录
```

空白安装刚结束为 **1 项目 / 0 任务**；日常 Skill 建卡后为 **1 / 1**；练习建项后为 **2 / 1**。最终确认把首任务移到 completed，不删除它。示例模式原有 2 项目 / 8 示例任务，安装仅增加系统项目；后续建真实首卡和练习项目后为 4 / 9。普通 `ember init` 只建骨架，空白为 0 / 0，示例为 2 / 8，不执行完整引导。

安装记录不是任务成果。日常 Skill 采用 `artifact_mode:none`，通过 `add_material(kind=input)` 保存 `installation.json` 的只读快照，`source_locator:ember-init:installation-receipt`；不创建虚假交付。用户最终确认后使用既有 `complete_task` 完成。

## 可执行边界

```text
<实际Python> <ember-init目录>/scripts/bootstrap.py --app-dir <新程序目录> --workspace <新文档库> --mode empty --name 余烬 --port 8783 --executor <实际工具>
```

两个目录必须为空或不存在、互不包含，执行器未知时用 manual，不填模型。脚本默认用附带 wheel，没有时才取同版本发行包；开发验证使用 `--source`。新版本发行前只使用配套本地候选包，不混用旧版安装脚本。

`installation.json` 的 `ready` 表示技术检查通过，不代表服务常驻或用户验收。报告路径为应用目录内绝对路径。失败不覆盖记录或重置目录；早于系统登记的失败也保留应用收据，但不谎报已有任务。技术测试只在脚本自建临时文档库进行。

默认工具通过 `ExecutorRegistry` 或现有 HTTP 接口保存，携带 revision 并保留其他工具。全局日常 Skill 使用 `install-skill --target <真实用户级目录>`，回读返回 path 下的 SKILL.md，遇到自定义副本不覆盖。日常 Skill 复制成功不代表客户端已热加载，当前 AI 应显式读取它再执行。

写入后用 GET `/api/state` 回读，并刷新工作台；只切换 hash 不会重取数据。运行服务时使用带 token 的 HTTP；离线写入由 `workspace_lock` 保护，不同时启动第二个服务。

最终移除接口是 POST `/api/onboarding/remove-init-skill`，payload `{task_id, confirmation:true}`。离线使用 `<程序Python> -m ember.onboarding_completion --workspace <文档库> --task-id <已完成首卡> --confirm`。只允许本次安装记录关联的已完成系统任务，且有实际日常和建项 Skill 历史。它只移除固定 `.agents/skills/ember-init`，保留程序内原版、下载包、其他全局副本和用户数据；直接手动删目录不是有效完成状态。

程序内原版可通过 `ember skill-path` 找到，用于以后创建新文档库。升级程序和 `install-skill` 不会自动恢复本库已移除的向导。已有工作区不自动升级或迁移，重复安装不能覆盖原库或旧收据。

## 验证

回归覆盖安装成功 / 失败、empty / example 数量、安装不建任务、普通建首卡、输入证据、项目查重与确认，以及最终移除的确认、任务关联、修改保护和重试。删除后必须验证 check / serve / health / settings 正常，项目任务仍在，两个日常 Skill 仍可用。发行前从最终三 Skill ZIP 与 wheel 做独立实装并回读，不能只测试源码。
